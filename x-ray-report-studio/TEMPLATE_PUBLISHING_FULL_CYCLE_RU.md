# XRS 0.4.86 — единый кандидат обновления шаблонов

Исходная Stable: `xrs-v0.4.85`, SHA `6e1e4aef65f042d8e78606621c38c4416d60f75e`.
Официальный действующий manifest находится в ветке распространения
`codex/mri-report-studio`; на момент начала работы он подтверждает 0.4.85 и
Setup SHA-256 `f346f9c9fcb667986896be0c520382f72b0e9b81717f8663e9ffe3ed9889dc34`.
Default main и исходный релизный тег не содержат актуальный публичный manifest.
Проверять нужно штатный STABLE_MANIFEST, а не случайную копию latest.json.

## Состав интеграции

Одна ветка приложения от проверенного кандидата 0.4.86 поверх 0.4.85.
Редакторские исправления не переписываются. Backend XRS-Templates компилируется
из проверенного checkout командой `scripts/sync-template-publisher.mjs`; его
точный commit и SHA-256 находятся в `electron/template-publisher-provenance.cjs`.
Снимок включает только публичный код/схемы/113 утверждённых источников.

Привилегированный main process проверяет PIN-сессию, фиксированный путь и хеш
компонента, запускает собственный EXE с ELECTRON_RUN_AS_NODE без shell и передаёт
один ограниченный запрос через stdin/stdout. NODE_OPTIONS/NODE_PATH/debug не
наследуются. Версия протокола и operationId обязательны. Неполный ответ,
повреждённый UTF-8, таймаут и несовместимая версия останавливают операцию.
Credentials и signing keys не передаются в renderer или диагностический журнал.

Для публикации backend проверяет официальный GitHub user/keyring владельца.
PIN не предоставляет удалённых прав. Stable разрешается только после явного
owner approval и действительного защищённого server flag; клиент не может
включить его локальным переключателем. Обычный клиент без owner credentials
публиковать не может. Технические тесты не активируют flag.

В существующем административном редакторе добавлены проверка изменений,
публикация Test/Stable, явное подтверждение точной версии, отслеживание состояния,
история, загрузка личной редакции из библиотеки и восстановление предыдущего
утверждённого содержания как нового Draft/новой подписанной версии.
Открытый пациентский протокол не используется как источник.

Статус PUBLISHED требует проверки реального подписанного Release, publicationId,
request hash, предыдущей версии, manifest SHA-256 и каждого изменённого пакета.
После доказанной публикации временные data refs очищаются; при неопределённом
результате повторный dispatch не выполняется вслепую. Workflow и signer остаются
на main; код из ветки данных не исполняется.

## Клиенты и локальные изменения

Используется существующая строка обновлений и TemplateCatalogStore.
Корень доставляется цепочкой последовательных переходов с порогами подписей
старого и нового root, сохраняется атомарно и проверяется при холодном запуске.
Только текущий неотозванный signer может подтвердить новый индекс. Исторические
пакеты читаются из ранее принятого поколения либо по точному хешу, заново
авторизованному текущим подписанным индексом; старый ключ не может выпустить
новый индекс самостоятельно. Это сохраняет Archived после ротации.

Пин первого root не берётся из интернета. После разрешённой первоначальной
настройки `scripts/embed-template-trust.mjs <approved public anchor.json>`
встраивает только проверенный публичный якорь в итоговую сборку. Приватный root
остаётся в зашифрованной USB-копии. До этого source.enabled=false/root=null.

Локальные шаблоны сравниваются как Base/Local/Incoming. Независимые структурные
изменения объединяются, пересекающиеся сохраняются для явного выбора.
Неизвестная база прежней локальной редакции не угадывается. Удаление из общего
каталога не скрывает сохранённый личный вариант. Сравнение показывает три
редакции с оформлением. Перед записью создаются backup и журнал восстановления;
сбой записи восстанавливает прежние overrides. Открытые документы не меняются.

Исправлена найденная при интеграции подмена локально выбранного поколения
последней глобальной Active-редакцией: metadata для администратора и рабочий
источник новых документов теперь используются раздельно. Явный выбор Archived
и глобальная история сохраняются.

## Проверки и единый RC

Workflow `xrs-full-template-release-candidate.yml` выполняет полный npm test,
build, реальные Windows Electron сценарии, внутренний clipboard, внешние
clipboard-фикстуры, 12→11 pt, отступ, 8 Spine v8/40 полей, историю, локальное
администрирование, DOCX/Chromium PDF, Offline AI Review и обновление из точного
опубликованного Setup 0.4.85. Проверяются SHA-отказ, ярлык, новый EXE/FileVersion,
холодный запуск, настройки, протокол и предыдущая установка.

`template-publishing-electron.mjs` использует два настоящих Electron и реальный
версионированный child process. GitHub API/расписание job — изолированная
синтетическая HTTPS-служба; подписи, SHA, пакет и клиентское хранилище настоящие.
Это не считается публикацией через GitHub Releases. Тестовый adapter существует
только в временной копии приложения; testFetch допускается только unpackaged.
Он не включается в RC. Production ключи в тестах не используются.

Установочный ZIP создаётся только через `--candidate-output test-output/rc-086`.
downloads/latest.json, updater приложения, Stable 0.4.85 и её установщик не
публикуются и не перезаписываются. CI artifact предназначен для единой приёмки,
а не для автоматического распространения всем врачам.

## Внешние условия перед общей ручной приёмкой

1. Отдельное решение владельца по merge проверенной инфраструктуры; PR №2
   автоматически не объединяется, защита main/Environment не меняется.
2. Разрешённый запуск Windows setup на административном компьютере владельца:
   официальный вход, защищённая авторизация, три пары ключей, отдельный физический
   носитель и проверенный зашифрованный root backup; Secrets через безопасный stdin.
3. Принятие публичного anchor/root/chain штатным защищённым процессом, встраивание
   подтверждённого anchor в финальный RC. Без первого pin полноценную production
   доставку нельзя считать настроенной.
4. Отдельное разрешение на реальную техническую Test-публикацию в GitHub и
   получение двумя Windows XRS. Это часть одного общего испытания, не отдельная
   пользовательская приёмка backend. Test не разрешает Stable автоматически.

Не отправлять токены, пароли или закрытые ключи в чат. Имена Secrets/Variables и
подробная защита сейчас недоступны интеграции (403); это не успешная проверка.
До выполнения этих условий PRODUCTION READY и STABLE RELEASED не заявляются.

## Один чек-лист ручной приёмки итогового RC

1. Обновить синтетическую установку 0.4.85 до единого RC; открыть прежний протокол.
2. Проверить внутреннюю/внешнюю вставку, курсив, 12→11, _А, Undo/Redo, DOCX/PDF.
3. В Spine v8 сохранить личную редакцию и последовательно заполнить два 0,0.
4. В управлении шаблонами сохранить Draft, проверить изменения, опубликовать
   синтетическую Test-редакцию из XRS; дождаться подтверждённого PUBLISHED.
5. На двух независимых Windows XRS проверить одинаковую доступную версию/hash
   и установить после подтверждения. Убедиться в сохранности открытого протокола.
6. Сравнить локальный конфликт, сохранить личный вариант; проверить историю
   и восстановление предыдущего утверждённого содержания новой Test-версией.
7. Выполнить холодный запуск, офлайн-проверку и локальный откат на одном клиенте;
   второй клиент и сохранённые документы должны остаться неизменными.
8. После общей приёмки отдельно решить вопрос Stable. До разрешения не менять
   защищённый flag и не публиковать каталог или EXE в Stable.
